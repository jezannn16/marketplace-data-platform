# Вопросы для технического интервью

1. **Какой поток данных реализован?** FastAPI-симулятор → Python ingestion → PostgreSQL raw → dbt staging и marts → Streamlit; Dagster управляет последовательностью ingestion и dbt.
2. **Почему данные воспроизводимы?** Генератор использует локальный `Random` с фиксированным seed и фиксированную начальную дату.
3. **Какие данные есть в симуляторе?** 100 товаров, 1000 заказов и по 3000 дневных записей остатков и рекламы; реальных клиентов нет.
4. **Как устроена пагинация?** Номер страницы начинается с 1, размер ограничен 100; сортировка выполняется по `(updated_at, id)`.
5. **Как выполняется инкрементальная загрузка?** Pipeline передаёт включительную нижнюю границу `updated_at` из `raw.ingestion_state` и повторно считывает записи на границе.
6. **Что происходит, если на одной границе много записей?** Все страницы границы считываются заново; primary key и upsert по ID не создают дубликаты.
7. **Когда продвигается checkpoint?** Только после проверки всех страниц ресурса, в транзакции записи последней страницы. Предыдущие страницы могут быть уже сохранены.
8. **Как восстановиться после сбоя?** Повторить запуск: чтение начнётся с прежней включительной границы, а записанные страницы будут безопасно применены повторно.
9. **Гарантирует ли это отсутствие потерь для любого API?** Нет. Offset без snapshot, поздние события ниже cursor и удаления требуют другой стратегии; текущая гарантия относится к неизменному набору симулятора.
10. **Как ограничиваются конкурентные загрузки?** PostgreSQL advisory lock сериализует ingestion одного ресурса; при занятом lock запуск ресурса завершается ошибкой.
11. **Как обрабатываются 429, 5xx и недоступность API?** Ограниченное число попыток, exponential backoff с jitter и учёт `Retry-After` в пределах максимальной задержки. Для остальных HTTP-ошибок повторов нет.
12. **Почему не dlt?** Для четырёх ресурсов выбраны httpx и psycopg, чтобы явно связать checkpoint и транзакции. Это требует поддержки собственного кода пагинации и восстановления.
13. **Что содержит raw?** Текущую версию записи с ID, `updated_at`, JSONB payload и временем загрузки. История версий и удалений не реализована.
14. **Что значит gross revenue?** В проекте это прокси суммы стоимости всех заказов, включая отменённые, по дате создания в UTC; это не бухгалтерская признанная выручка.
15. **Почему net revenue и ROAS равны NULL?** Нет возвратов, правил признания и связи заказов с рекламными кампаниями; приравнять эти показатели к нулю было бы неверно.
16. **Как рассчитан stock coverage?** Последний известный остаток / средние неотменённые заказанные единицы за последние 30 дней. Это оценка; при нулевом спросе, отсутствии снимка или разных датах складов значение NULL.
17. **Какие проверки есть в dbt?** `unique`, `not_null`, `relationships`, `accepted_values`, а также SQL-инварианты и сверка агрегатов с staging.
18. **Как Dagster обрабатывает ошибку ingestion?** Asset dbt зависит от raw; при сбое raw он не запускается. Sensor может уведомить о сбое, если Telegram явно включён.
19. **Что показывает freshness?** Возраст последней успешной обработки ресурса и отдельно cursor источника. Это не SLA и не проверка реальной полноты данных.
20. **Что требуется до production?** Контракт настоящего API и snapshot/late-data стратегия, права и секреты, TLS/аутентификация, надёжная оркестрация и мониторинг, бизнес-правила, реальные объёмы и проверенное восстановление.
