# Использование Codex при разработке

Проект создавался итеративно с Codex по запросам пользователя: фундамент, симулятор API, ingestion, dbt и локальный операционный слой. Код, SQL, тесты, конфигурация и документация генерировались и затем проверялись выполнением инструментов. Решение оставлять net revenue и ROAS неопределёнными следует из отсутствующих данных и согласованных бизнес-правил, а не из знания реального продавца.

Подтверждённые проверки в ходе разработки включали pytest с отдельным PostgreSQL 16, dbt build, Ruff, реальный локальный запуск Dagster с симуляцией 500 и последующим восстановлением, Streamlit AppTest и Compose config. Предыдущий GitHub Actions run коммита `44108be` прошёл на GitHub; состояние более новых коммитов следует проверять в Actions. Доступность Docker Engine на машине разработки и выполнение backup/restore нельзя считать подтверждёнными без отдельной проверки.

Во время финального аудита исправлены открытые внешним интерфейсам локальные порты API/PostgreSQL, root-пользователь приложения в Dockerfile, устаревшее описание dbt-зависимостей, риск удаления нетестовой БД интеграционными тестами и вычисление coverage по снимкам складов с различными датами. Добавлена CI-проверка Compose; её результат зависит от выполнения на runner. Проверка имени тестовой базы уменьшает вероятность ошибки, но не доказывает безопасность подключения. AI-авторство не заменяет code review, независимый security audit и валидацию бизнес-правил владельцем данных.

Инструменты выполняли код и тесты; результаты не следует считать нагрузочными испытаниями, production-опытом или подтверждением работы с реальными данными маркетплейсов. Данные в проекте синтетические, сообщения в Telegram в ходе этих проверок не отправлялись.
